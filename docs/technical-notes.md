# intro4k

Framework for a 4 KB intro: procedural 3D textures, rendered as lit volumetric clouds. It uses the same brick system as the Vulkan RTX demos, ported to OpenGL compute + a software brick traversal so it fits a 32-bit Crinkler build.

```
intro4k.sln
src/
  main.cpp          Win32 + OpenGL host (Debug: hot reload, Release: Crinkler entry point)
  config.h          resolutions, volume sizes, quality, duration (shared with the shader)
  intro.glsl        every pass in one source
  minify.bat        Release pre-build: intro.glsl -> shader.h
  bake_config.ps1   Release: config.h values written into a copy of the shader (baked/intro.glsl)
  embed_shader.ps1  fallback embedder when Shader Minifier is missing
tools/              put crinkler + shader_minifier here (see tools/README.txt)
bin/                output exes + crinkler_report.html
```

## Frame pipeline

World space is the unit box `[0,1]^3`, so a world position is directly a volume uv.

| Pass | Stage | Size | Does |
|---|---|---|---|
| 0 noise | compute, once | `NOISE_SIZE^3` R16F | tileable gradient FBM (cloud shaping, erosion, cloud layer) |
| 1 density | compute | `TEXTURE_SIZE^3` RG8 | `density(position)`: cloud density, tree occupancy |
| 2 bricks | compute | `BRICK_COUNT^3` RG8 | per brick of `BRICK_SIZE^3` texels (+1 texel border): has cloud, has tree |
| 3 light | compute | `LIGHT_SIZE^3` RG16F | R = optical depth from each voxel to the light, G = sky visibility |
| 4 render | compute | `XRES x YRES x RENDER_SCALE²` RGBA16F (+ mips when `RENDER_SCALE` > 1) | camera rays, clouds, matte ground, cloud layer, night sky lit by the moon (the moon itself is not drawn), height fog, lightning, god rays (linear HDR) |
| 5 audio | compute, once | `AUDIO_WIDTH x AUDIO_ROWS` RG32F | the soundtrack, stereo (see Sound) |
| 6 post | fragment, `glRects` | screen | strike color split, bloom, ACES, color grade, gamma (no antialiasing: the clouds are soft) |

The brick grid replaces the BLAS/TLAS of AABBs. `marchBricks()` walks it front to back with a 3D DDA, skips empty bricks and marches occupied ones with a fixed global step:

- **clouds** accumulate in order (front to back), so compositing is exact, unlike the unordered any-hit version.
- a camera ray stops once the cloud is opaque (`OpaqueOpticalDepth`).
- the **light pass** and the **floor shadow rays** use the same `marchBricks()` without shading.

Every pass is the same source compiled with a different `#define _P n`. In Debug, `main.cpp` prepends the config values (`_TS`, `_BC`, …) as defines; in Release, `minify.bat` bakes them into a copy of the shader before minifying (`bake_config.ps1`), so the exe only carries `#version 430` and the pass id. `main.cpp` also prepends the stage glue: `_I` is the invocation id or pixel, `_O` is the output color.

## Building

- **Debug|x86**: normal exe with the CRT. Reads `src/intro.glsl` at runtime and recompiles every time you save it. Errors show in the debugger output and the window title, and the last working shader keeps running.
  - The window keeps 16:9 when resized and the render scales to it (letterboxed when maximized).
  - Debug renders at `DEBUG_XRES x DEBUG_YRES` (`config.h`, 1280 x 720), not `XRES x YRES`: about 2.25 times fewer pixels for the render pass while tweaking on a laptop. `main.cpp` redefines `XRES`/`YRES` to them in Debug, so the shader header, the render target, the dispatch and the window (opened at that size) all follow; the volumes keep their sizes. Release (`bake_config.ps1` reads `config.h`) still renders `XRES x YRES`.
  - `SPACE` pause, `LEFT`/`RIGHT` seek (`SHIFT` = faster), `BACKSPACE` restart, `ESC` quit. The soundtrack follows: it is the clock while it plays and restarts from the new time after a seek or a pause.
  - The frame rate is capped at `DEBUG_FRAME_RATE` (`config.h`, 30) to keep a laptop cool: each frame sleeps away the rest of its 1/30 s, whatever the refresh rate. `L` toggles the cap. The title shows the frame time and the frame's own render time (measured after `glFinish()`), which the cap does not hide.
  - `M` mutes the soundtrack, `F5` saves it to `bin/intro4k.wav`. The title shows the audio render time and peak (`CLIPPING` if any sample hits full scale). Saving `intro.glsl` renders the soundtrack again.
  - Free camera: `UP`/`DOWN` or `W`/`S` fly, `A`/`D` strafe, `Q`/`E` down/up, left mouse drag to look, `SHIFT` = faster. `C` returns to the shader camera (the camera plans, as in Release). The shader takes it through the `_C(position, forward)` hook in `renderPixel()`. In Release, `bake_config.ps1` removes that call from the baked shader, so the Release glues of `main.cpp` have no `_C` (keep the call on a line of its own).
  - Camera plans, for working on the cameras: the intro is cut into `SHOT_COUNT` plans of `SHOT_DURATION` seconds (`config.h`: 10 plans, 0 to 9; plan 0, the prologue, lasts `PROLOGUE` (20 s), the others 10 s; the last plan runs until `DURATION`, 114 s, so plan 9 lasts 14 s and pans over all of it). The prologue (the credits and the title) comes before the scene clock: the shader gets `PROLOGUE` as `_PR` (`Prologue`), and its `time` is the clock minus `Prologue`, so every time of the scene (the storm timeline, the strikes, the heartbeat break, the apocalypse, the logo, the fades) is in scene seconds and plays 20 s later on the clock: plan 0 shows the calm deck as the scene starts, fading in from black over the first `FadeIn` seconds (5 s, the picture as a rising exposure in `renderPixel()`, the sound with it). Only the camera plans, their cuts and the fade-in follow the clock (`planCamera()`, `PlanStart()` / `PlanAt()` in `main.cpp`). The cut at the end of the prologue (20 s) gets its strike like the others. Each plan has a start view and optionally an end view, taken from the free camera and kept in `src/cameras.txt`: one line per view with `position=vec3(...)` and `forward=vec3(...)` (box units) and the free camera yaw and pitch.
    - The plans are the camera of the intro, in Release too: `planCamera()` in `intro.glsl` reads them from `_CM`, 10 integers per plan (start view, end view: x y z yaw pitch in hundredths), and pans linearly over each plan like the Debug playback. Debug: `main.cpp` writes `_CM` from `cameras.txt` (`PlanDefines()`) and recompiles the shader when the file changes. Release: `bake_config.ps1` writes them into `baked/intro.glsl` at each build (`cameras.txt` is a build input). A plan without a view holds the view before it. Cost: ~200 bytes compressed for 9 plans.
    - `0`-`9` go to plan n: its start time and start view. With `SHIFT`, just before its end, with its end view. The soundtrack restarts there.
    - `F6` saves the free camera as the start view of the current plan, `F7` as its end view: with both, the camera pans from one to the other over the whole plan, at constant speed (the cut lands on an already moving camera). Saving again replaces the view.
    - `DELETE` removes the end view of the current plan (static again), then its start view.
    - The Debug build plays the recorded plans from the start, with the soundtrack; a plan without a view shows the shader camera, which holds the view before it. Seeking and `0`-`9` keep playing them from the new time. Flying the camera or `C` stops the playback (the free camera stays where it was, ready for `F6`/`F7`), `T` stops or plays it again. `cameras.txt` is read again when it changes, so hand edits show at once.
    - The title shows the current plan. `cameras.txt` is read again before every change and rewritten in plan order: hand edits of the values are kept, comments are not.
  - The working directory must be `src/`. Visual Studio's default is fine.
- **Release|x86**: no CRT, entry point `entry`, size flags, shader embedded by `minify.bat`: `bake_config.ps1` replaces the `_XX` macros of `intro.glsl` by the `config.h` values (in `src/baked/intro.glsl`, generated), then Shader Minifier writes `shader.h`. Shader Minifier sees plain numbers and folds them into the constants.
  - `bake_config.ps1` also writes the integer config values read as floats (`float(_SD)`, `float(_PR)`...) as float literals (`10.`): Shader Minifier keeps `float(10)` as it is but folds `10.` into the expressions around it (-30 bytes). `minify.bat` runs Shader Minifier with `--aggressive-inlining`: every constant is written where it is used, which Crinkler compresses better (-30 bytes). Same values, same code. And with `--field-names rgba`: the swizzles are written `.rgba` instead of `.xyzw` (the same components), which Crinkler compresses about 25 bytes better on this shader (`stpq` is 50 bytes worse).
  - With `tools/link.exe` (renamed Crinkler), Crinkler links and compresses.
  - Without it, the MSVC linker runs instead. You get warnings about the `/CRINKLER` options and an uncompressed exe that still runs.
  - `FULLSCREEN 1` (`config.h`): a borderless window over the whole screen (`GetSystemMetrics`), no display mode change. The `XRES x YRES` picture is scaled to the largest centered viewport of its aspect that fits the screen (black bars): the post pass covers the whole screen and does the fit itself, in its Release glue (`main.cpp`): `_V` is the screen size (`glUniform2i`, set once at startup), `_W` x `_R` the picture rectangle (the same integer rounding as a viewport), `_I.xy` the screen pixel mapped back into the picture with its sub-pixel fraction, so the upscale is filtered and the texts are drawn at the screen resolution, and `_I.z` 1 inside the picture, 0 in the bars (`intro.glsl` multiplies the color by it). No `glViewport` and no `glClear`. It costs `glUniform2i` in the Release name list, two `GetSystemMetrics` and the uniform; the glue assumes a 16:9 `XRES:YRES` (a `static_assert` checks it). `FULLSCREEN 0`: a borderless `XRES x YRES` window at the top left of the screen, no scaling, one exe per resolution. The process is DPI aware, so a Windows display scale does not enlarge the window. It quits at `DURATION` and on `ESC`.
  - Hybrid laptops: `NvOptimusEnablement` / `AmdPowerXpressRequestHighPerformance` make the driver use the discrete GPU. Only Debug exports them (`dllexport`, `FORCE_DISCRETE_GPU` in `config.h`). Release does not: Crinkler ignores `dllexport`, and its `/EXPORT:name=0x00000001` cost 76 bytes (dropped on 2026-10-16). On a hybrid laptop, the Release exe runs on the GPU Windows picks: choose the discrete GPU for `intro4k.exe` in Settings > System > Display > Graphics, or in the NVIDIA / AMD control panel.
  - The Crinkler options are only passed when `tools\link.exe` exists.
  - Crinkler `/TINYIMPORT` (since 2026-10-16, -100 bytes): the imports are found at startup by a hash of their name in the DLLs' export tables, with less code and no name strings. Crinkler warns that it may break if a future Windows version adds functions to one of the imported DLLs (kernel32, user32, gdi32, opengl32, winmm), and recommends shipping a version linked without it too: remove `/TINYIMPORT` from `intro.vcxproj` for that build (about 100 bytes larger, over 8 KB). The DLLs are Windows', not the GPU driver's, so an exe that starts on your Windows starts on the same Windows version elsewhere.
  - Crinkler `/HASHSIZE:500` (its default) and `/SATURATE`: with 200 MB the hash table lost 15 bytes to collisions, `/SATURATE` keeps the model counters from wrapping on the repetitive shader text. Both only change the decompressor (500 MB while it unpacks), not the intro. `/COMPMODE:VERYSLOW` saves 1 more byte for 5x the link time; `/TEXTPART:YES`, `/TRANSFORM:CALLS` and `/UNALIGNCODE` were measured worse or equal.
  - Crinkler `/REUSE` with `src\crinkler.reuse`: Crinkler's model search is greedy, and a 2-character change can make it pick a set of models that costs 30 bytes more. The reuse file keeps the best configuration found so far (models, section order, hash size): each build compresses with it and with a fresh search, and keeps the smaller ("Reverting to reuse configuration" in the log when the file wins; it is rewritten when the fresh search wins). Keep it with the sources. Crinkler writes its reuse file as a link output, which Clean and Rebuild delete: the build works on a copy in `obj\Release`, copied from `src` before the link and back after the build (`intro.vcxproj`), so `src\crinkler.reuse` survives a Rebuild. After a shader change, the log warns that the old shader section is not present: expected, the new one is added. Delete the file to start from a fresh search. Since 2026-10-18 its models are tuned beyond Crinkler's own search: a script changed the data models one at a time (context mask, weight, removal), each candidate linked with `/REUSEMODE:ALL` (about 6 seconds), and kept every change that made the exe smaller; then the hash table size. On the 2026-10-18 shader that is about 70 bytes less than Crinkler's best fresh search (16 data models instead of 21). Do not delete the file: a fresh search would lose that. On 2026-10-19, about 40 expressions of `intro.glsl` (32 lines) had their operands put in the other order where that changes nothing in the arithmetic: `a * b` -> `b * a`, `a + b` -> `b + a` (two simple operands only, never across a chain like `x / a * b`), `a < b` -> `b > a`, `dot(a, b)` -> `dot(b, a)`. Each was linked with the tuned models and kept only if the exe got smaller (-45 bytes in all, from a search over 600 candidates). So the operand order of some lines (`12.9898 * n`, `rayEnd > brickEntry`, `age * 30.0`...) looks arbitrary: it is chosen for the compressor, leave it as it is. On 2026-10-20 the same search, wider: operands that are calls or parenthesized (`(1.0 - tornadoGrowth()) * WallCloudHeight`), declarators of one declaration in the other order when independent (`float t = dot(toA, direction), along = ...`), and adjacent functions of a section in the other order when neither calls the other (`tornadoGrowth()` now before `stormActivity()`, and so on). One swap, `exp(-distance * decay)`, changed the rounding on Mesa (its compiler reorders a multiplication by a constant, here the one inside `exp`): it was left out, and the result was compared bit for bit at 10 times. A GPU compiler that reorders multiplications can still round a last bit differently somewhere: invisible. Operands that call a function with `out` parameters (`cutStrike()`, `strike()`, `planCamera()`...) keep their order: the call writes a variable the other operand reads. Nor is a factor swapped in a product that is then multiplied by a constant (`opticalDepth * max(stepLength, 0.0) * CloudExtinction`) or that sits inside `exp()`: the compiler reorders multiplications by constants, and the rounding would change. On 2026-10-28, three more kinds of reordering: the two arguments of `min`, `max` and `dot` (`max(0.0, x)`), the difference inside `abs()` and `length()` (`abs(WallCloudHeight - height)`), two parameters of a function, in its definition and at every call (`capsule()` takes `rb` before `ra`, `cloudLighting()` its ray direction first), and two adjacent statements that are independent (neither reads nor writes what the other writes; no call that writes a global or an `out` parameter), for example two declarations in the other order. Compared bit for bit: the whole soundtrack, and every pass at 12 times. Measure with Shader Minifier on .NET (Windows, or .NET 8 elsewhere), not on Mono: the same exe names a few local variables differently under Mono (in `thunder()` and `pad()` on 2026-10-28), so a size measured with Mono can be off by a few bytes (8188 measured, 8190 built). On 2026-10-29 the same searches again with the .NET minifier: `rayToSegment()` and `floorColor()` take their parameters in the other order, and a few more operands and statements moved (8190 -> 8188). One swap, in `heartBreak()` (`return a * b;`), changed the last bit of 184 soundtrack samples: the function is inlined where its result is multiplied by a constant, and the compiler reorders that chain. It was left out: a product returned by a function keeps its order. On 2026-11-02 (8244 -> 8200) the same searches plus two more kinds of reordering: statements two lines apart, and adjacent global declarations. On 2026-11-03: `solidLighting()` names its constant offset `i_texel`. The `i_` prefix tells Shader Minifier to inline the variable at each use (`vec2(1./320,0).rgg`...), which changes nothing in the arithmetic (-6 bytes). Then a sweep of 300 random hash table sizes instead of 80 (-2 bytes). The output is bit-identical to the 8244 shader. In reserve: rounding the pad chord frequencies to 0.1 Hz (`587.3` instead of `587.33`...: at most 0.06 cent, inaudible) was worth -3 to -7 bytes.

Shader Minifier's `--format c-variables` names the string after the file: `intro_glsl`. If your version names it differently, rename it in `main.cpp`.

## Where to work

In `intro.glsl`:

- `density(position)`: the scene, a cloud density in 0..1: the storm (R) and the trees and shrubs (G, solid occupancy).
- Trees (`treeSolid()`): `TreeCount` (3) dead trees standing on the plain around the storm, swaying in the wind as it builds (`TreeSway`), uprooted from touchdown on: the first at touchdown, the other two together `TreeUproot` (4) s later, with the big cut strike (`treeUproot()`), and carried around the funnel, tumbling, each on its own orbit (`treePivot()`, `treeLocal()`). Tree n has its own size (`treeHeight()`: `TreeHeight` for the first, the others smaller), shape (the seeds of its branches), place and flight. They are solids in the density volume: its G channel is the solid occupancy (the volume and the bricks are RG8). `treeDistance()` is a signed distance (a trunk flaring at the root, `TreeBranches` branches of random angle, rise and length, three twigs on each, bent by a gnarl at two scales), its surface inflated by `TreeInflate` so the branches are at least a texel or two thick, turned into an occupancy with the surface at 0.5 (`clamp(0.5 - d x DensitySize x 0.25)`: a ~4 texel band, smooth enough for the normals). `marchBricks()` stops a camera ray where it crosses the 0.5 iso-surface (refined linearly with the previous sample) and shades it with `solidLighting()`: `TreeBark`, normal from the occupancy gradient, the moon through the clouds (the light volume looked up slightly outside the surface), the sky light dimmed in the creases, the strikes. A light ray adds `SolidOpticalDepth`, so the trees cast shadows on the clouds and the floor. Each tree is evaluated only inside its bounding sphere (the density pass runs for every texel).
- Shrubs (2026-10-18, in place of the debris branches: about -206 bytes estimated, and a density pass about 40% faster): trees 3 to 7 of `treeSolid()` (`TreeCount` 8), the same shape at a quarter to a third of the first tree's height (`treeHeight()`), standing nearer the storm between the trees (0.17 to 0.27 from the center), uprooted one every `ShrubUproot` (2.5) s after touchdown and carried around the funnel on random orbits in the range of the trees' (`flight` in `treePivot()`). `treeSolid()` now tests each tree's bounding sphere around its pivot before computing its own coordinates (the rotations and the sway only for the texels near it): 1.05 x its height (the old 0.75 plus 0.3 for the sway of the top); the three trees render the same.
- Tornado (the clouds, in `density()`): a funnel hanging from a rotating wall cloud, with a debris whirl at its base. `tornadoAxis()` makes the axis snake with height and time, and `tornadoRadius()` sets the funnel profile. `tornadoCoordinates()` gives noise coordinates turning with the vortex (angle, radius, height), which both the shapes and the erosion use, so the detail turns with them. `TornadoSpin` is a rigid spin: a radius-dependent spin would wind the noise up over time. Also `TornadoRise` and `WallCloudHeight`, plus `CloudColor` for the storm-grey tint.
- Storm timeline (scene seconds: the clock minus `Prologue`, 20 s): a calm cloud layer (plans 0 and 1), then from `CumulusStart` (10 s) the layer above the box starts turning around the axis (`stormActivity()`, over 10 s) and lowers into a wall cloud. From `TornadoFormationStart` (20 s) the funnel tip descends from it (`tornadoGrowth()`) and reaches the floor at `TornadoTouchdown` (35 s). The debris whirl and the uprooting of the trees start there. The soundtrack and the lightning follow the same functions, so they move with these times. The intro ends with a `FadeOut` (5 s) before `DURATION`: the image fades to black (in `renderPixel()`, as a falling exposure: the dark parts go first, the lit clouds last) and the sound fades out later, over the last `SoundFadeOut` (2 s): the storm still rumbles on the black screen.
- Cloud layer: one deck at `CloudLayerHeight` that the tornado grows out of. `storm()` blends its noise (`layerNoise()`, slow drift) into the vortex noise near the axis (`swirlWeight()`), so the funnel is the same cloud. Inside the box it is part of the volume. Outside it, out to the horizon, `marchCloudLayer()` evaluates the same density directly (`CloudLayerSamples`, 3 light samples each), before and behind the box, with `layerOutsideVolume()` handing over between the two. `layerOpticalDepth()` adds its shadow to the floor and the light volume. `CloudLayerWind` (box sizes per second) blows it across the sky past the anchored storm, `CloudLayerChurn` changes its shapes as it goes, `CloudLayerCoverage` sets the gaps; each sample is fogged at its distance, so the far layer fades into the fog. Cost: one more march per sky pixel, plus the shadow samples.
- Cloud lighting (`cloudScattering()`): direct light through a few multiple-scattering octaves plus a diffusion term (`CloudDiffusion`, `CloudDiffusionStrength`: light through thick cloud falls off as a power of the optical depth, not exponentially), plus the sky light times a sky visibility. In the storm, `cloudLighting()` adds two terms. The sky visibility from the light pass (`skyVisibility()`: transmittance of short rays along the 6 axes, `SkyVisibilityRange`, never below `SkyVisibilityFloor`) darkens dense cores. A form term uses the outward direction of the full-resolution density (gradient over `FormOffset` texels, `FormStrength`), so the funnel, only a few light voxels wide, shows its sides and twisted striations instead of one flat shade. Elsewhere both are 1, matching the directly evaluated layer. Light rays never stop early (only camera rays stop, past `OpaqueOpticalDepth`): a cap gave every voxel of a dense core the same optical depth, which looked like a clamped color.
- `erodeCloud()`: per-sample detail erosion, at a higher frequency than the volume, drifting with the layer and turning with the vortex. The directly evaluated layer uses it too, and its light paths subtract its mean, so both halves of the layer match.
- Moonlight: the only light is the moon, fixed at `MoonDirection` (~47 degrees up). It casts the shadows, its color (`MoonLight`) comes from the atmosphere transmittance, and the sky it scatters is the ambient light (`SkyLight`). Its illuminance is 1, so `Exposure` sets the brightness and `ColorGrade` gives the cool moonlit look (the teal and orange comes from the color grade of the post pass).
- Sky section: `skyRadiance()` is an analytic fit (within 3%) of single scattering through a Rayleigh + Mie + ozone atmosphere (Hillaire 2020 parameters), lit by the fixed moon: Rayleigh in-scattering saturating along the view path, the Mie glow around the moon, and horizon extinction. `MoonLight` (moon illuminance after the atmosphere) and `SkyLight` (zenith radiance, the ambient light) are constants. (The final intro no longer draws this sky: the clouds cover it, so `skyRadiance()` and its fitting script were removed; `MoonLight` and `SkyLight` stay as constants.)
- All lighting uses the moon constants directly: `MoonDirection`, `MoonLight`, and `LightDistance` for the shadow rays (beyond the box).
- `renderPixel()`: camera. `skyColor()`, `godRays()`: environment.
- Fog section: height fog for the limited, apocalyptic visibility. Its density is `FogDensity` at the ground and falls by e every `FogHeight` upward; `fogTransmittance()` integrates it along a ray in closed form. `withFog()` mixes each element toward the fog color by its own distance: every cloud layer sample, the volume at the box entry, and the floor or sky behind. So the horizon and the far deck dissolve while the deck overhead, above most of the fog, stays visible. On top of it, a distance fog: none up to `FogNear` (1.5), opaque at `FogFar` (5). It hides the far cloud layer, which the height fog barely reaches, and the layer march stops at `FogFar`, so its samples stay dense enough (no marching artifacts near the horizon). The sky is fogged as if at the top of the box, so the far gaps of the layer show fog too. `FogColor` is the moonlit dust color. Both fogs thicken with the apocalypse: the density and the distance (so the vision limit comes closer) are multiplied by 1 + `ApocalypseFog` (1.5) x `apocalypse()`, so the storm swallows the far mountains and the cloud layer toward the end, except during the heartbeat break, where the view clears as the storm steps back (`heartBreak()`, moved up next to `apocalypse()` with `BreakStart`/`BreakEnd` so the fog can use it). About +24 bytes.
- Lightning section: `updateLightning()` (once per render invocation) cuts time into `FlashInterval` slots. Each slot has a strike with probability `FlashProbability`, from `LightningStart` (3 s) on, at a random moment in it: a few fast flickers decaying in ~0.4 s, at a random point of the deck near the storm. `flashLight()` adds `FlashColor` (warm, cream to orange) with a `1 / (1 + FlashFalloff x distance²)` falloff to the ambient light of the clouds (volume and layer) and to the floor; `FlashFogGlow` lights up the fog. No shadowing: the light is scattered inside the clouds.
- Lightning bolts (`boltLight()`): the strike flashing has a visible bolt, from the strike point in the cloud base (`flashPosition`) down to the ground (`boltBottom`, a random point under it). `BoltSegments` (24) straight segments whose inner points are offset at random (`BoltJag`) on a slow meander (`BoltWander`), plus a fork leaving the channel at a random point and dimming to its tip. Each strike has its own shape (`flashSeed`: its slot, or its cut), kept through its flickers, and the bolt flickers with the flash. It is light emitted along the camera ray, by the angle between the ray and the nearest point of each segment (`rayToSegment()`): a thin core (`BoltCore`, ~2 pixels) and a glow (`BoltGlow`, `BoltGlowStrength`), `BoltColor` x `BoltBrightness`. Opaque cloud hides it and the fog in front dims it. The strike also lights the ground where the bolt hits (`GroundFlash`, in `flashLight()`).
- Texts written by lightning (`logoLight()`): the REBELS logo over the last camera plan and the fade, on the right half of the screen; the credits and the title over the prologue (camera plan 0). `LogoPoints` holds them one after another, a pen lift (-1,-1) between them, each as polylines in its own units (x right, y down from its top left corner): an approximate trace of the logo (96 x 113: the emblem outline, its counter and slot, and the letters), the credits (`ck`, `teo`, `ska`, one per line, left aligned: lowercase letters 12 high, 13 apart, lines 26 apart) and the title (`WHISP`, capitals 20 high, 80 wide). Per text the arrays `TextFirst`, `TextCount` (its points), `TextCorner` (top left corner, screen heights from the screen center), `TextScale` (screen heights per unit), `TextStart`, `TextDraw` (stroke time) and `TextEnd` place and time it: the credits from `CreditsStart` (12.5 s before the scene, 7.5 s on the clock) over 2 s on the left, faded out at `CreditsEnd` (12.5 s on the clock); the title from `TitleStart` (5.2 s before the scene, 14.8 s on the clock) over 1.5 s on the right, faded out at `TitleEnd` (0.3 s before the scene, 19.7 s), just before the cut strike ending the prologue; the logo from `LogoStart` (9 s before the end, in the last camera plan, before the fade) over 3 s, 0.45 screen high, until the end. The strokes of a text strike one after another, each brighter for a moment as it lands, then crackle (a sideways jag of `LogoJag` units, re-drawn 25 times a second, zero at the stroke ends so the corners stay joined) and flicker, fading out over the second before its end. Each stroke is a core (`LogoCore`) and a glow (`LogoGlow`, `LogoGlowStrength`) in `BoltColor` x `LogoBrightness`, drawn by the post pass (`postProcess()`, after the bloom, before the tonemapping) over the picture, so the logo stays on the black screen. They are not in the render pass: there the loop over the segments slowed every frame, even when skipped; `logoLight()` also skips it when no text is on screen. Their sound is `logoCrackle()` (audio pass, filter 9): sparse sparks through a bright band (3.5 kHz), a burst on each 25 Hz re-draw of the jag, thicker while the strokes strike, at `LogoCrackleGain` (0.25), played over the sound fades and fading with the text on screen. Cost: ~750 bytes (the logo ~390, the credits ~190, the title ~100), mostly the points.
- Sheet lightning: dim flashes deep in the distant cloud layer, with no bolt and no thunder. At most one per `SheetInterval` (1.2 s, `SheetProbability` 0.6), at a random moment in it, at `SheetDistance` to twice that (4 to 8) from the storm in a random direction: `updateLightning()` sets `sheet` (position, and intensity with the strikes' `flicker()`), and `marchCloudLayer()` adds `SheetColor` with a wide falloff (`SheetFalloff`) to the light of the layer samples outside the box. So it only shows where a plan sees the far deck (not in the prologue's view down into the box), a soft patch of sky lighting up and flickering, up to ~15% of the frame brightness. About 70 bytes.
- Eye adaptation (post pass): after each strike the picture dims, `AdaptDepth` (30%) at most, as its thunder reaches the camera, and recovers with it: the same `thunderAt()` value as the strike color split, so close strikes and the cut strikes dazzle more, at no extra cost. Heartbeat pulse (post pass): during the heartbeat break the picture brightens `HeartPulse` (25%) on each beat, lub then the softer dub, in time with the sound: `heartAge()` gives the beat timing to both `heartbeat()` and `postProcess()`. On the same beat the colors split `HeartSplit` (0.6 of the strike split), and between the beats the eye loses focus: the picture blurs toward the mip level `HeartBlurLevel` (3) below the screen, `HeartBlur` (80%) at most, snapping sharp on each beat and fully blurred in the silence before the end of the break (about +11 bytes for the split and the blur). The strikes light the mountains too (`flashLight()` in `intersectMountains()`). About 60 bytes for the three.
- Bloom (post pass): what is brighter than `BloomThreshold` in the mip levels below the screen level (`BloomLevels` = 7 wider and wider blurs, `BloomStrength` each) glows around it: the bolts, the strikes, the lit clouds. `main.cpp` allocates the mip levels of the HDR target (`COLOR_LEVELS`) and generates them each frame.
- Heartbeat kick, flare on the beat, rain on the lens (2026-10-23, post pass): on each heartbeat the view punches in `HeartKick` (3%) and the lens flare swells (`FlareBeat`, x3 at the beat). In time with the rain sound (`stormActivity()` x (1 + `apocalypse()`), as `RainGain`), rain runs down the lens, and none during the heartbeat break: in `LensDensity` (25%) of `LensColumns` (40) columns a streak falls at its own speed, bending the picture behind it like a drop (`LensRain`) and catching the light (`LensGlint`, +30%); soft across its column.
- Grass (`grass()`, 2026-10-18, about +140 bytes estimated, render pass up to ~10% slower on the frames with a lot of floor): short grass on the plain, a layer `GrassHeight` (0.012) thick marched in `GrassSteps` (16) samples at fixed heights from its top down, on the camera rays that reach the floor. The plain is cut in cells of 1 / `GrassDensity` (250) with one blade in each, at a random place and of a random height, tapering to its tip and leaning `GrassBend` (1.5) cells in gusts rolling over the plain (harder with the apocalypse), and toward the funnel as it comes down (`GrassPull`, 1: the inflow, x `tornadoGrowth()`, strongest about 0.14 from the axis; about +16 bytes estimated). Under the funnel the ground is bare: the grass shrinks to nothing within 0.3 x `GrassBare` (0.16) of the axis, full height from `GrassBare` on, x `tornadoGrowth()` (about +18 bytes estimated). The first sample inside a blade stops the ray: `floorColor()` there (so the cloud shadows, the strikes and the fog apply), tinted `GrassColor` and darker toward the root. The layer thins with distance, gone at `GrassFar` (3), where the blades would be smaller than a pixel. A camera below the grass top would see it wrongly (the scripted plans stay above 0.04).
- Rain and dust (`marchAir()`): rain curtains hanging from the cloud base around the storm, and after touchdown dust on the ground spiralling into the funnel. They are thin, so they are not in the density volume (their bricks would no longer be skipped): `marchAir()` marches them on their own along the camera ray, `AirSamples` (12) samples each, inside the cylinder of radius `RainRadius` around the storm. Rain (`airDensity()` part 0): shafts turning slowly with the storm with fine vertical streaks falling fast, between `RainInner` and `RainRadius`, heavier on one side, fading into the cloud base (`RainTop`), growing with `stormActivity()`, `RainDensity`, `RainColor`. Dust (part 1): logarithmic spiral arms winding in (`InflowSpin`), hugging the ground (`DustHeight`), with the debris ramp after touchdown, `DustDensity`, `DustColor`. Both are lit by the moon through the clouds (the light volume), the sky and the strikes (`airLight()`), and fogged. The march is split at the storm axis: what is in front of it is drawn over the storm, the rest behind it. Nothing within 0.1 to 0.3 of the camera (the camera plans often fly inside the rain: close rain would veil the whole frame).
- Ground mist (`marchAir()`, part 2): low wind-blown banks hugging the plain out to `FogFar`, thicker here and gone there, so the plain reads in layers (near, middle, far) instead of one floor plane under one cloud plane. Its density is a noise (`MistScale`, drifting at `MistWind`) thresholded into banks, `MistDensity` at the ground falling by e every `MistHeight`, marched with `AirSamples` up to `MistTop`. It has the rain's light (`airLight()`: the moon through the clouds, the sky, the strikes), and the near-camera fade of the rain. Its own grey albedo (`MistColor`); the banks drift along x and slowly change shape. About 50 bytes.
- Cut strikes: a strike hides each camera cut, between two plans (`cutStrike()`, at n x `SHOT_DURATION` for the cuts inside the intro; the shader gets `SHOT_DURATION` and `SHOT_COUNT` as `_SD` and `_SC`). `cutFlicker()` pre-flashes `CutLead` (0.12 s) before the cut, puts the full flash on the cut frame itself, then fades with a few flickers; `CutFlash` (1.5) is its brightness relative to the other strikes. Its thunder is heard at once, like a close strike, so the crack lands on the cut. They happen in Release too, every `SHOT_DURATION`, ready for the camera plans.
- Mountains section: a ring of mountains painted on a cylinder wall of radius `MountainRadius` (2.5) around the storm (reworked on 2026-10-16 for size: about -66 bytes estimated against the raymarched height field). `intersectMountains()` intersects the wall analytically (the far side, so a camera outside the ring, as at the start of plan 1, sees the far side through the near one) and keeps the hit where it is under the ridge line: `MountainHeight` x (two noise octaves along the heading)^2 - `MountainBase`, the low gaps sinking under the floor. It is shaded flat: `MountainAlbedo` lit by the moon through the average cloud layer (`FloorDistantShadow`, at a fixed 0.2), the sky and the strikes (`flashLight()`). It replaces the floor or the sky when hit first, so the fog dissolves it like the background: dark rolling ridges in the fog, at a real distance, so they move with the camera. No march, no normal, no terrain for a camera to fly into.
- Floor section: infinite matte ground at y = 0. `FloorAlbedo` is its dusty color, `FloorVariation` the contrast of its large lighter and darker patches (they give the scale and the camera motion). It gets the shadows of the clouds and the cloud layer around the storm, up to `FloorShadowRadius` from its axis, faded out over `FloorShadowFade`. Further away it gets `FloorDistantShadow`, the average transmittance of the layer, and skips both shadow marches. That saves the shadow rays on most floor pixels and keeps the ground calm around the tornado's shadow. Strikes light it too (`flashLight()`), and the fog hides it with distance.
- Color grade (post pass): `grade()` works on the tonemapped image, a cinematic teal and orange. Split toning tints the shadows and midtones toward `ShadowTint` (teal) and the highlights toward `HighlightTint` (warm), so the moonlit clouds stay teal and only the areas a strike lights up go cream and orange. `GradeSaturation` raises the saturation, and after gamma an S curve (`GradeContrast`, 0 = none) deepens the shadows. The tight `FlashFalloff` keeps that warm light local to the strike.
- Thunder camera shake: `thunderShake()` jolts the view direction when the thunder of a strike arrives, as the sound does: delayed by the distance (`ThunderDelay`), at once on the cut for a cut strike, stronger for a close strike, faint before the first cut, fading in about `1 / CameraShakeDecay` s. `CameraShake` (0.02 rad for a close strike) sets the strength, which grows to x2 with `apocalypse()`. It shakes the free camera too (Debug).
- Apocalypse strike color split (post pass): `apocalypse()` climbs from `ApocalypseStart` (40 s) to 2 s before the end and drives the sound and the split. The thunder heard from the camera (`thunderAt()`, the same as for the camera shake and the surge of the sound: it lands with the thunder, weaker for far strikes, fading by e in `1 / StrikeSplitDecay` s) splits the colors toward the edges (`StrikeSplit`: red outward, blue inward), as strong as `apocalypse()`. The post pass gets the clock too (`glUniform1i` in `RenderFrame()`) and calls `planCamera()`.
- `CloudExtinction`, `CloudScattering`, `AirScattering`, `Exposure`: look constants at the top of the file `Exposure` is 4.4 for the party projector (it was 2.6 for a monitor): the mid tones of a typical frame went from ~40 to ~70 of 255 and the prologue from ~22 to ~40, with ACES rolling the highlights off. The cut strikes were already white flashes. Raise it further if the projector is dim, lower it back for a monitor.
- `marchBricks()`: the traversal shared by camera rays, the light volume, and the floor shadows.

The source is written for reading. Shader Minifier renames everything for the Release build, so long names cost nothing. The short `_XX` macros are the config values (`main.cpp` defines them in Debug, `bake_config.ps1` writes their values in Release) and the stage glue; the shader reads them once, into readable constants. Without Shader Minifier, the fallback embeds the readable source as-is, which is fine for testing but far too big for the 4K.

In `config.h`:

- `TEXTURE_SIZE` and `BRICK_SIZE`: resolution vs update cost. The density pass evaluates `density()` for every texel, every frame.
- `LIGHT_SIZE`: shadow sharpness on the clouds.
- `STEP_SCALE`, `GODRAY_SAMPLES`: march quality.
- `RENDER_SCALE`: supersampling (2 = 4x the render cost). The render target then gets mip levels (`glGenerateMipmap`, only compiled in then) and the post pass reads the screen-size level, so it is a box downsample: the only antialiasing.
- Every volume size must be a multiple of 8 (compute groups are 8x8x1).

## Sound

The soundtrack is pass 5 of `intro.glsl` (section `sound`), rendered once on the GPU before the first frame: `RenderAudio()` dispatches it, `glGetTexImage(GL_RG, GL_SHORT)` reads it back as 16-bit PCM (the float to short conversion clamps to -1..1), and `waveOut` plays it in one buffer. The Release clock is `waveOutGetPosition()`, so picture and sound cannot drift. The passes get it as the integer sample position (`uniformSample`, `glUniform1i`), and `main()` in the shader turns it into `time` with the same formula as `soundtrack()` uses for each sample of the audio pass (Debug passes its float clock converted to samples).

- **Blocks + warm-up:** each invocation renders `AUDIO_BLOCK` consecutive samples, after running `AUDIO_WARMUP` samples from silence so the sequential filters have settled. With 4096 the blocks match a continuous run within -110 dB. A filter that self-oscillates never settles: keep the Moog resonance under ~0.8.
- **Synced with the scene:** `time` is a global set per sample, so the sound reads the same timeline as the picture. The thunder has no sound of its own: `thunderAt()` hears the strikes of `strike()` and `cutStrike()` from the camera of the plans (`planCamera()`), delayed by the distance (`ThunderDelay`, seconds per box size, at once on the cut for a cut strike) and attenuated, and it swells the storm sound (`SurgeGain`, `SurgeDecay`) as it shakes the camera. The wind howls up with `stormActivity()`, the tornado roar grows with `tornadoGrowth()`, pulses with `TornadoSpin` and doubles at touchdown, when the debris knocks start (same ramp as the debris whirl) along with a sub drop. A low drone swells with the storm.
- **Precision:** at 120 s a float time has ~8 us of resolution, too coarse for audio phases. The noise hashes the integer sample index and envelopes use small ages.
- **Precision of tones:** the drone uses `tone()`, a whole number of samples per period, so its phase is exact at any time.
- **Filters:** `moog()` is the 4-pole lowpass of the raspberry-sampler (`filter_lowpass.h`), the roar uses its wave folder (`fold()`, `filter_distortion.h`).
- **Layers:** `WindGain`, `RoarGain`, `DebrisGain`, `CrackGain`, `RumbleGain`, `DroneGain`, `SubGain` balance them (hot reload in Debug; `F5` to check the file).
- **Size:** this full version costs roughly 700 compressed bytes of shader (estimate). `backup/audio-lean/intro.glsl` has a lean sound section (wind, roar and thunder only, unfiltered crack: ~200 bytes less) to copy over when optimizing.

Release builds the pass headers from one string, `passHeader`, whose pass digit is incremented after each program, instead of 7 strings and a pointer table (-29 bytes). The Release glues have no `#define _C(p,f)`: `bake_config.ps1` removes the `_C(...)` call instead. The intro stops when the waveOut sample position reaches `DURATION * SAMPLE_RATE` (an integer compare, no float constant). The clock goes to the shader as that sample position (`glUniform1i`), not as float seconds: no int to float conversion and no float constant on the CPU side (-35 bytes). The shader lets GLSL convert ints to floats where an int meets a float (`n / SampleRate`, `AudioWidth * frequency`, `invocation + 0.5`) instead of writing `float(...)` or `vec3(...)`: the same conversion, the same code, 7 characters less each (-30 bytes). Keep the integer divisions on the int side: `n / AudioWidth * x` divides as ints first, like `float(n / AudioWidth) * x`. Textures: each is set up on unit 0, then `glBindTextures` binds texture units 0..4 and `glBindImageTextures` image units 0..5 in one call each (GL 4.4), from the names array `textureNames`, instead of `glActiveTexture` and one `glBindImageTexture` per texture; Release no longer loads `glActiveTexture` (-34 bytes). waveOut: setting `WHDR_PREPARED` in the static `waveHeader` instead of calling `waveOutPrepareHeader` saves a call (-4 bytes on 2026-11-02; not applied: it relies on Windows accepting a header it did not prepare).
